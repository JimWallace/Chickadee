# Dependency updates

Dependencies update by default. A person or an agent is involved only when an
update fails.

## The flow

1. **Dependabot opens a PR** (`.github/dependabot.yml`). Packages that pin each
   other are grouped, so each PR resolves on its own. The pip
   `jupyterlite` / `jupyterlite-core` split in #2863 is why.
2. **`dependabot-auto.yml` lands it.** When the bump feeds committed output, the
   workflow regenerates that output on the Dependabot branch first:

   | Bump in | Committed output | Regenerated by |
   |---|---|---|
   | `Tools/vendor/package*.json` | `Public/vendor/` | `scripts/setup-vendor.sh` |
   | `Tools/jupyterlite/chickadee-extension` | its labextension and `Public/jupyterlite/extensions/@chickadee/` | `jlpm build`, then `scripts/vendor-chickadee-extension.sh` |
   | `Tools/jupyterlite/requirements.txt` | `Public/jupyterlite/` | `revendor-kernels.yml`, dispatched with `commit: true` |

   It then enables auto-merge. The required checks on `main` decide the merge:
   a green PR merges, a red PR waits, and `auto-release.yml` deploys a merge as
   it deploys any other.
3. **An issue reports each failure.** The label is `dependency-update-failed`,
   and there is one issue per problem (`scripts/dependency-issue.sh`).
   - `dependency-failure.yml` reports a red check on a Dependabot PR, with the
     failed jobs, the end of the log and a brief for an agent.
   - `dependency-health.yml` runs each Monday. It reports a Dependabot PR that
     has not had auto-merge for three days, a security alert that has had no
     PR for a week, and a `RELEASE_TOKEN` that is broken or near expiry. It
     closes each issue whose problem is gone.

Once a regeneration commit is on a Dependabot branch, Dependabot no longer
rebases that PR. If `main` moves and the branch falls behind, the PR waits,
and the weekly sweep reports it as stalled.

To resolve one, point an agent at the issue. The brief in the issue states the
rules: fix forward, skip no test, and add an `ignore` entry with a reason only
when the new version cannot work here.

## When Dependabot cannot fix a security alert

Dependabot does not raise a transitive package past its parent's range. Its job
fails with `security_update_not_possible`, and no PR opens. For a package that
is used only at build time and ships nothing, force the fix:

- npm: `overrides` in `package.json`. The root forces `minimatch` past
  `eslint`'s range.
- Yarn: `resolutions` in `package.json`. The extension forces `katex` (pinned
  through `mermaid`) and `sanitize-html` (pinned by `@jupyterlab/apputils`).

Show that the build output does not change, or that CI passes. Remove the
entry when the parent's range admits the fix.

## The tokens

A merge or push made with `GITHUB_TOKEN` starts no workflow, so nothing would
tag or deploy the merge. The ruleset also refuses its pushes. The automation
therefore uses a fine-grained personal access token on this repository. It
needs Contents, Pull requests and Workflows (read and write), and Dependabot
alerts (read).

| Secret | Where | Read by |
|---|---|---|
| `RELEASE_TOKEN` | Actions secrets | `auto-release.yml`, `revendor-kernels.yml`, `dependency-health.yml`, and runs that a regenerated commit starts |
| `DEPENDABOT_MERGE_TOKEN` | Dependabot secrets | Runs that Dependabot starts. They cannot read Actions secrets |

`dependency-health.yml` checks `RELEASE_TOKEN` each week and on any PR that
changes the workflow. `dependabot-auto.yml` checks its token at the start of
every run.
