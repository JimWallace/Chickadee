### Fixed

- **The browser runner's wasm loader no longer loses its WASI shim when the build layout changes.** `PackageToJS` in JavaScriptKit 0.56.1 decided whether a module needs WASI by reading the target triple out of the build artifact's directory path. That guess is correct only for one layout: SwiftPM's newer Swift Build engine puts the artifact in `.build/out/Products/...`, so the inferred triple became the literal string `Products`, the WASI branch of the loader template was compiled out, and the vendored `runner-core.js` shipped without the shim the module still imports. The result was a silent failure — the build reported success with zero warnings and the size-budget check passed, while the module could not instantiate (`Import #17 module="wasi_snapshot_preview1": module is not an object or function`). JavaScriptKit 0.59.0 derives the answer from the module's own import table instead, so it holds for any build system or output layout. `wasm/Package.swift` already allowed the newer version; only the resolved pin moved.
